# Анализ базы Front

---
**Закупка**

основные: bm_StorageOperations, bm_JournalBarnetDocs
связанные: product, vendors, bm_JournalTypeDocuments, bm_StorageOperationsType

**bm_StorageOperations** - это главная таблица, потому что в ней лежат сами операции: сколько товара пришло, на какую сумму, от какого поставщика
- DocumentID - ссылка на документ, например 1 
- OperationID  тип операции, например 1
- ProductID - товар, например 4368
- VendorID - поставщик, например 200
- Count - количество, например 2.5
- Amount - сумма, например 455.0

Сверху справа **bm_JournalBarnetDocs** - это суть конкретного документа
- ID - ключ, например 1
- DocumentTypeID - тип документа, например 4
- Period - дата, например 2023-11-11
- Amount - сумма, например 954.0

суть состоит в том, что через один документ много операций проходит, поэтому линия идёт от документа к операциям, и на конце у операций стоит «много» по идее


**bm_JournalTypeDocuments** - справочник типов документов по ID (например 4) и Description (например поступление продуктов) и тут по идее связь идет от одного ко многим

**bm_StorageOperationsType** - справочник операций 
там ID (например 1) и Description (например поступление) так же связь должна идти от одного ко многим

**product** - это справочник товаров
- id - ключ, например 2345
- productid - код, например 12345
- description - название, например бекон 

от продукт к операциям идет связь один ко многим
один товар может быть во многих операциях, то есть по идее сам товар у нас лежит в product а его внешние операции/движеиня в bm_StorageOperations

**vendors** - справочник поставщиков
- id - ключ, например 65
- firstname - название, например ИП Вкусняшка

от vendors идет связь к операциям
но она пунктирная, потому что внешнего ключа в базе нет
то есть по факту же связь есть, потому что поставщики есть а внешнего ключа нету

**Продажа**

основные: journal, bm_Journal_Details
связанные: product, transtype, bm_JournalSessions, personnel

**journal** - это главная таблица по продажам, потому что в ней лежат строки чеков
Одна строка = одному товару в чеке

- transnumber - ключ строки, по нему цепляются детали, например 1
- receiptn - номер чека, например 12345
- transtype - тип операции (продажа, покупка, ожидание, ошибка ... ), например 404
- dater - дата и время, например 2023-12-06
- description - товар, например соус кетчуп
- quantity - количество, например 1
- amount - сумма, например 50.0

**bm_Journal_Details** - это детали строки чека
- ID - ключ, например 1
- SourceID - ссылка на journal, например 1
- ProductID - товар, например 7650
- BludoID - блюдо, например 4822
- Quantity - количество, например 1
- Count - количество по составу, например 0.08

суть в том, что от journal к нашей таблице идет связь один ко многим 


**product** - справочник товаров
- id - ключ, например 4368
- productid - код, например 12345
- description - название товара, например бекон

от product к bm_Journal_Details идет две связи и обе один ко многим то есть один товар может быть много раз в деталях


**transtype** - справочник типов операций
- transtypeid - ключ, например 101
- description - название типа, например sales

от transtype к journal идёт связь один ко многим

**bm_JournalSessions** - сессии сотрудников
- ID - ключ, например 1
- PersonID - сотрудник в сессии, например 1
- DateAdd - дата сессии, например 2023-12-06
- Type - тип события, например документы


**personnel** - справочник сотрудников
- personid - ключ, например 1
- lastname - фамилия, например Иванова
- firstname - имя, например Анна

от personnel к bm_JournalSessions идёт такая же по идее только логическая связь один ко многим, поэтому пункитом

**Поставщики**

основные: vendors
связанные: vendorgroup, bm_Contracts, bm_Companies, bm_StorageOperations, pricelist

**vendors** - это главная таблица по поставщикам, потому что в ней лежат сами поставщики
один поставщик = одна строка

- id - ключ, например 91
- clientgroup - группа, например 31
- firstname - название, например ИП Иванов
- INN - ИНН, например NULL

**vendorgroup** - справочник групп поставщиков
- vendorgroupid - ключ, например 31
- description - название, например поставщики

от vendorgroup к vendors идёт связь один ко многим 


**bm_Contracts** - договоры
- ID - ключ, например нет строк
- VendorID - поставщик, например нет строк
- CompanyID - организация, например нет строк
- ContractNumber - номер договора, например нет строк

тут таблица пустая, так что непонятно зачем она вообще там или просто никто легально не хочет работать ХАХАХА


**bm_Companies** - организации
- ID - ключ, например 6
- CompanyName - название, например ИП Иванов Антон Игроьевич
- INN - ИНН, например 380122679974

от bm_Companies к bm_Contracts идёт связь один ко многим 


**bm_StorageOperations** - складские операции
- ID - ключ, например 1
- VendorID - поставщик, например 200
- ContractID - договор, например 1
- Count - количество, например 2.5
- Amount - сумма, например 892.00

то есть тоже опять же связи нету, но по логике должна быть


**pricelist** - цены
- id - ключ, например 1
- productid - товар, например 4377
- vendorid - поставщик, например NULL
- basecost - базовая цена, например 0.0

и тут тоже самое со связями - логические только

- ID - ключ, например 1

- DocumentTypeID - тип документа, например 6

**bm_CashOperations** - кассовые операции
- ID - ключ, например нет строк
- PersonID - сотрудник, например нет строк

**Остатки**

основные: bm_StorageOperations
связанные: bm_StorageOperationsType, bm_JournalBarnetDocs, product, storages, stockperiod

**bm_StorageOperations** - это главная таблица по остаткам, потому что в ней лежат движения товара
Одна операция = одна строка

- ID - ключ, например 1
- DocumentID - документ, например 1
- OperationID - тип операции (поступление, списание ... ), например 1
- ProductID - товар, например 4368
- StorageID - склад, например 41
- Count - количество, например 2.7
- Amount - сумма, например 892.7
- DateAdd - дата, например 2020-11-15

**bm_StorageOperationsType** - справочник операций
- ID - ключ, например 1
- Description - название, например поступление
- Factor - коэффициент, например 1

от bm_StorageOperationsType к bm_StorageOperations идёт связь один ко многим по айдишнику

**bm_JournalBarnetDocs** - документ
- ID - ключ, например 1
- Period - дата, например 2021-11-11
- DocumentTypeID - тип документа, например 4

от bm_JournalBarnetDocs к bm_StorageOperations идёт связь один ко многим по айдишнику

**product** - справочник товаров
- id - ключ, например 4368
- productid - код, например 12345
- description - название, например бекон
- onhand - остаток, например NULL

от product к bm_StorageOperations идёт связь один ко многим по айдишнику

**storages** - склады
- id - ключ, например 41
- description - название, например скклад

от storages к bm_StorageOperations идёт связь один ко многим по айдишнику

**stockperiod** - периоды остатков
- id - ключ, например 56
- productid - товар, например NULL
- quantityin - приход, например 25000
- quantityout - расход, например 50
- datebeginperiod - начало периода, например 2024-01-01
